## ad4114_sample_manager 模块

一块板子 16 路 AD5560，用 2 片 AD4114。总共 8 个板子，16 片 AD4114 使用同一个 SPI。

i_start 后 16 片 AD4114 依次初始化配置。

初始化配置流程：复位（等 500us），回读 ID （应为 0x30D），配置各寄存器（滤波、采样模式）。

单片 AD4114 配置：8 通道差分采样、20ms 滤波，不开增强型、连续采样，采一圈 160ms。

所有初始化配置完成后进入 ST_POLL 状态，读取 ADC 采样结果，先拉低 cs，等一段时间后查询 miso 是否拉低，代表是否有数据，有数据则读，没数据则切换下一个。

每次有数据则 sample_valid = 1。skip_cnt 可以选择几个点输出一次，用于切档稳定。

模块输出：数据、以及数据对应的通道号、哪一片 AD4114，用以对应是哪个 AD5560 的数据。

## measurement manager 模块

根据数据的 id 判断是哪个 ad5560 的数据，存到相应地址的 ram 中。

负责 V/I 切换，每次某通道采样一个数据后就切换，等下次再采都是 160ms 了，数据应稳定了。

默认切换的很快，相对于 160ms 来说肯定切完了。

保存 vi_state[128] 根据这个区分数据是电流还是电压，存入不同的地方，每次切换后更改对应 bit 状态。

关键是切换的时候要切 gain （0x1）和 measout 输出（0x2），不同电压、电流挡位要选择不同的 gain。

电压 gain 根据 FIN DAC 决定，电流 gain 根据电流挡位决定。

初版调试实现：仅实现存储，暂不实现自动切换 V\I。上位机手动切换先测。

## config manager 模块

外部上位机通信直接写模块内部的 ram，写完后发送执行指令给 system 模块。

system 模块把执行指令分成两部分，先发 crc_start 进行 crc 校验，校验通过再发 cfg_start 开始配置。

模块内部状态机基本上就是读 ram 数据。

该模块控制多条总线是阻塞式的，一条一条指令写入，写完再下一条指令，如果当前总线忙则等待。

## 新的并行 config manager 模块

1. 新增并行执行，不再是阻塞式，8 条总线并行执行，方法是加 8 个 ram，各总线命令分别放。
2. 新增 delay 指令，用于分组控制。

crc_start 指令先校验内部 ram 种的 crc 是否正确（与原有模块功能一致）。

并行执行，方法是搞 8 个 ram，每个 bus 一个，先把 config ram 的指令根据 bus_id 分发给 8 个 ram。如果遇到 delay 指令，就暂停分发，先让各个 bus 把 ram 中的执行完，再统一 delay 完以后再继续执行余下的。

一个仲裁器，仲裁 8 个 bus 的指令，总的 config 模块只有一个提交出口 + bus_id。提交很快，一个 clk 就提交了，提交以后 driver 自己运行 spi，内部可以仲裁下一个 bus 的提交。

bus_executor 和仲裁器的逻辑理解：

bus_executor 主要信号：

`i_load`: Config 往指定 BUS 的 RAM 中写一条命令

`i_start`: 本阶段分发结束，所有 Executor 开始执行

`o_valid`: BUS 的队首命令已经准备好，可以被仲裁器选中

`i_take`: 这条命令真正被 Driver 接收，通知被选中的 Executor 弹出队首

`o_pending`: 是否还有未提交的命令（也就是本次 start 是否结束，整个阶段完成标志）

`command_take`: 公共接口真正握手成功

仲裁器主要信号：

`rr_next`: 下一轮从哪个 BUS 开始搜索（仲裁器轮询起点）

`bus_valid`: 8 个 Executor 哪些已经准备好队首命令。

`pick_bus`: 本次选中的 BUS。

`pick_valid`: 是否找到了可以执行的 BUS。

第一个阶段，config 分发指令，先用 `i_clear` 清空，再使用 `i_load` + `i_record`，将读出来的指令根据 bus_id 进行分发。

第二个阶段，，`i_start` 控制所有 bus_executor 开始执行

仲裁器根据 各 bus_executor `o_valid` 以及对应 bus 的外部 driver 是否 ready i_cfg_bus_ready 来选择 bus 输出给外部 driver（pick 以后 cmd_valid = 1）。

然后等待外部 driver 接收握手 `command_take` 后，rr_next + 1，同时把握手信号传给对应 bus_executor，让其继续读下一条指令。

### 组合逻辑仲裁器设计思路

组合逻辑中，for 循环是可以综合出来带优先级的电路的，比如 if...else if... 这种，因此理解 for 的意义时，可以按照顺序串行推演：

> 读代码时，可以按照 for 循环的**顺序串行**推演；理解综合后的硬件时，要把它看成同一时钟周期内工作的组合优先级网络，也就是**优先编码器**。

代码中 if 判断中 `!pick_valid` 的写法是个比较固定的，每次变量变化，组合逻辑重新计算，`pick_valid` 初值为 0，for 循环串行计算，某个 bus 满足条件，`pick_valid` 置 1，后续的 for 循环都不再判断。类似于 if...else if... else if，其中一个满足，后边就不执行了。

这种用来寻找**第一个满足条件**的，可以用这种写法。如果不加 `!pick_valid` ，那么 for 循环后续的判断会把值**覆盖**，变成了寻找**最后一个满足条件**的。

> for + !found 实际就等价于 if / else if 这种有优先级的写法。

## IO 控制逻辑

FPGA 直接提供控制 iic io 扩展器寄存器的读写命令，上位机先设置 16 路为输出，再设置 16bit 的输出值，这样 fpga 不需要初始化 iic io 扩展器。

REG|用途|DATA|
0x02|设置 16 路输出|0x0000～0xFFFF|
0x06|配置 16 路方向|0x0000 全部输出|

上位机通过，bus_id、addr 可以找到哪一片 io 扩展器，然后通过 reg_addr 和 reg_data，直接对其寄存器进行写值。

要点：
- 多个 bus 切换的时候要等一段稳定时间。
- 400k iic 频率。
- 使用 token 方式的 iic_master_core 模块。

现在温度 IIC 和 IO 扩展器共用同一个模块，根据是哪个模块判断写入的顺序。温度 IIC 提供的接口也是直接读、写温度芯片的寄存器。
这两个区别就是读写流程、字节数不一样，用模块信号区分一下，做在同一个状态机中。

0x00	—	ADT7461 自身温度，1°C 精度分辨率
0x01	—	AD5560 远端温度高字节
0x10	—	AD5560 远端温度低字节
